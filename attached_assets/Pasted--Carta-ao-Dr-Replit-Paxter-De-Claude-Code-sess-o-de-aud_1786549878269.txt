## O que está sendo montado

O Dr. Caio quer um segundo cérebro em Obsidian. A intenção dele é explícita e vale repetir: **não é documentação do sistema atual.** É a memória que vai servir quando ele construir os próximos — sistemas para outras clínicas, para comércio, para outros domínios.

Ele é médico, está aprendendo arquitetura de sistemas na prática, e quer sair deste projeto com entendimento transferível, não só com um sistema funcionando.

## O que é Obsidian, em uma passagem

Uma pasta de arquivos `.md` em texto puro no disco. Sem banco, sem servidor, sem formato proprietário — versionável com git, legível em qualquer editor. O aplicativo acrescenta links `[[assim]]` entre notas, backlinks automáticos (cada nota mostra quem a cita), frontmatter YAML com propriedades, tags, busca full-text, um grafo das conexões, e um plugin (Dataview) que consulta as notas como se fossem tabelas.

Em termos que você reconhece: é markdown num diretório, com indexação de referências cruzadas por cima. O cofre está vazio hoje.

## O que preciso de você

**1. A fronteira entre repositório e cofre.** Esta é a questão central e você é quem melhor a responde. O que pertence ao repo — `README`, `docs/`, comentários, o próprio código — e o que pertence ao cofre? A regra que tenho usado é grosseira: *no repo, o que descreve o estado atual do código; no cofre, o que descreve por que chegamos nele*. Isso resiste ao uso? Onde ela falha? O maior risco é duplicar informação nos dois lugares e uma das cópias apodrecer sem aviso.

**2. Registro de decisão de arquitetura.** No mundo do software isso tem forma consagrada — ADR, *Architecture Decision Record*: contexto, decisão, alternativas descartadas, consequências. Vale adotar o formato padrão, ou você propõe um mais enxuto para uma operação de uma pessoa com agentes? Um ADR que exige meia hora não será escrito.

**3. Postmortem sem cerimônia.** O modo de falha desta semana foi um commit desfazendo outro sem ninguém ver. Isso é ouro puro — é a classe de erro que vai reaparecer no próximo sistema, com outra roupa. Qual é o registro mínimo que preserva o **aprendizado** e não só o incidente? E qual o gatilho para escrever: toda falha? Só as que custaram tempo? Só as que se repetiram?

**4. O que você consultaria.** Inverta a pergunta. Imagine que daqui a um ano você é acionado para começar um sistema novo, de outro cliente, e tem acesso a este cofre. **O que você gostaria de encontrar lá para não repetir o trabalho e não repetir os erros?** Liste as notas que você abriria no primeiro dia. Essa lista, para mim, vale mais do que qualquer teoria de organização — ela define a estrutura de trás para frente, a partir do uso.

**5. Runbooks e o que é operacional demais.** Procedimento de deploy, variáveis de ambiente, o que fazer quando o serviço cai: parte disso é específico da instância e morre com ela, parte é padrão reaproveitável. Como você separaria o descartável do transferível? E o cuidado óbvio: **nada de segredo, token, credencial ou identificador sensível no cofre** — ele é texto puro, sincronizado, e vai durar mais que qualquer chave.

**6. A camada didática.** Ele não é engenheiro. Quando você registrar uma decisão de arquitetura, ela precisa ser legível por alguém que está aprendendo os conceitos agora. Como você escreveria uma nota que documenta a decisão **e** ensina o princípio por trás dela, sem virar aula longa? Se o cofre só ele conseguir ler daqui a um ano, funcionou; se precisar de você para traduzir, falhou.

**7. Onde minha proposta está errada.** Desconfio de `60-Lancamento/`: nasceu do momento atual do projeto e provavelmente não deveria ser pasta. E desconfio da numeração das pastas, que ordena bem mas engessa. Diga o que você cortaria.

## O critério

Ele quer entendimento e soluções reaproveitáveis — não um arquivo morto. O teste é simples: **o segundo sistema tem que começar melhor do que este começou.** Se o cofre não fizer isso, não serve.

Responda com estrutura concreta: pastas, nomes, campos de frontmatter, modelos de nota. E, se puder, um exemplo real — pegue uma decisão de arquitetura que você tomou neste projeto e escreva a nota como ela deveria ficar no cofre. Um exemplo bem feito ensina mais que a descrição do formato.
