**ENTROU.** Olhe atrás da caixa de diálogo: o Painel de Controle, a fila de validação de anamnese, os menus do Ato Médico, Cockpit da Consulta, Clientes, Exames. **Seu sistema está no ar e você está dentro dele.**

A caixa que apareceu não é erro. É outra porta — deixa eu confirmar de onde ela vem.

A caixa vem do **api-server**, não do padcom. Confirmei: o padcom não tem senha própria — ele só tem `VITE_API_SERVER_URL`, ou seja, ele **chama** o api-server para buscar os dados.

O que acontece na sequência:

```
1. Você entra no site          → api-server devolve seu token   ✓
2. Site redireciona pro padcom → você chega na tela             ✓
3. Padcom pede os dados        → api-server responde 401
4. O navegador vê o cabeçalho  → mostra essa caixa nativa
```

## E aqui está o problema de arquitetura que isso revelou

**Seu token ficou para trás.**

O login guardou o token no navegador, no domínio `padaxor.lovable.app`. O padcom vive em `workspacepadcom-production.up.railway.app` — **outro domínio**. Navegador não deixa um domínio ler o armazenamento do outro. É proteção, não defeito.

Então o padcom recebe você **sem token nenhum**, pede dados ao api-server, e o api-server responde com a senha de perímetro — a caixa que você viu.

**A passagem de sessão entre o site e o sistema não existe.** O login funciona; a sessão não viaja.

Isso é exatamente a decisão que eu levantei há dias como pendente: *"depois de entrar, a pessoa vai para onde, e como leva a credencial junto?"*. Ninguém decidiu, e o código foi escrito assumindo que redirecionar bastava.

## Para entrar agora

Preencha a caixa com o usuário e senha de perímetro — as variáveis `ADMIN_USERNAME` e `ADMIN_PASSWORD` que estão configuradas no api-server. **Você as definiu; eu não consigo lê-las** (o Railway devolve mascarado).

Se não lembrar, dá para ver no painel: serviço `@workspace/api-server` → aba Variables.
